# Security review: 18-save-progress, round 1

Reviewed 1 November 2026 against `git diff main...factory/18-save-progress` (tip `e6953e4`), the spec's 18 "Done when" statements and threat model, and `build.md` with its six decisions. Read only; no code changed. Secrets were searched with `git grep` only, and no `.env*` file was opened.

## Findings

No must fix findings. No should fix findings. Four notes.

1. **Note (the builder's question about the break-on-purpose result).** `supabase/migrations/20261031234601_save_progress_note.sql` lines 52 to 58 and 69 to 73 (the explicit `s.user_id = caller` checks), with `evidence/break-db-no-owner-check-only.txt` and `evidence/break-db-definer-only.txt`. Removing the explicit owner checks alone turns nothing red, because the learner's own read rule on `sessions` (`learners read their own sessions`, `user_id = auth.uid()`) refuses another learner's session too. I judge this acceptable, and I do not ask for a change. The two protections are each proven alone by the evidence: with `security definer` and the explicit checks kept, only test 3 (the invoker test) goes red and the other learner test (23) stays green, so the explicit check holds alone. With the explicit checks removed and `security invoker` kept, test 23 stays green, so the read rule holds alone. Removing both turns 3, 23, 18 and 29 red. The one gap is that no ordinary test fails if someone later removes only the explicit check. That change is harmless today, because the read rule still refuses, and test 3 fails if anyone makes the function `security definer`, which is the only way the read rule stops helping. If the owner wants the stricter form of the AGENTS.md lesson, the fix is one more pgTAP case: as the database owner, add a temporary permissive select policy on `sessions` inside the rolled back transaction, then check learner C still gets `'none'`. That proves the explicit check without the read rule. Optional.
2. **Note.** `supabase/migrations/20261031234601_save_progress_note.sql` line 33 (`auth.jwt() ->> 'is_anonymous'`). The guest decision reads a claim in the learner's token. PostgREST has already checked the token's signature, so a learner cannot forge it. A token stays valid for up to an hour after a guest adds an email, so a copy of the old token on another device could still be told "guest" and get the word `'first'` or `'reminder'` for that learner's own session. The only result is a note on that learner's own screen. Job 11 swaps the cookies on the device that added the email, and the `@email` test checks that. No action.
3. **Note.** `src/screens/FinishScreen.tsx` lines 73 to 80 (the `pageshow` guard). It is a small, safe precaution (it only hides the note) and no test proves it, as `build.md` says. It stores nothing and sends nothing. No action. If a later job removes it, the Back button test in `e2e/save-progress.spec.ts` is the only protection.
4. **Note.** `worker/api.ts` lines 341 to 346 (the `catch` that logs nothing). A failure of the note call is swallowed with no log line, so a broken function would never show up in the owner's crash reports. That is what the spec asks for (no learner data in logs, and the note can never break saving). It is a monitoring blind spot, not a leak. The job 14 analytics already count first sessions, so a note that never appears would have to be noticed by hand.

## Looked at closely, and passed

- **Grants and revokes.** The migration revokes all from `public`, `anon`, `authenticated` and `service_role` on `public.save_progress_note(uuid)`, then grants execute to `authenticated` only. pgTAP tests 7, 8 and 9 check `anon`, `service_role` and `PUBLIC` from the catalogue, and test 10 calls it as `anon` and expects `42501`. The evidence shows red runs for "granted to anon" (7 and 10) and "public left out of the revoke" (7 to 10). Function is `stable` (test 4, with a red run), `security invoker` (test 3, with a red run) and has an empty `search_path` (test 5). Every object inside the function is schema qualified (`public.sessions`, `public.usage_events`, `auth.uid()`, `auth.jwt()`), so the empty search path breaks nothing.
- **Can it leak anything about another learner?** It takes a session id but no learner id. The event read is filtered by `e.user_id = caller` and by the read rule on `usage_events`. The 'first' branch needs `s.user_id = caller` and the session read rule. The 'reminder' branch numbers only the caller's own sessions and looks the given id up inside that list, so another learner's id is simply not found. Every refusal is the same word, `'none'`, with no error, so the function cannot be used to ask whether a session id exists or who owns it. Test 23 (learner C, whose own event names learner B's session) and test 24 (another learner's third session) prove it, and the unknown id and null id tests (tests 16 and 17) return `'none'` with no error.
- **Can it leak anything about a signed in account?** An email account, or a token with `is_anonymous` false or missing, gets `'none'` before any table is read (tests 19 to 21, each changing only the claim). The answer reveals only whether the caller is a guest with a particular session, which the caller already knows. It does not reveal the email, the account id or any count.
- **Can it write?** `stable` makes Postgres refuse any write inside it. Tests 31 and 32 count the events and open sessions after all the calls. The repository test (`tests/save-progress-rules.test.ts`) fails on `create table`, `alter table`, `create type` or `alter type` in the migration, with a red run saved. The migration holds only the function, its comment and the grants.
- **The Worker.** `worker/api.ts` asks the function only after `completeSession` returned, with the same learner client (the learner's own token from the cookie). The no cookie case answers 401 before any database call, and a spy test shows the function is never called. The learner id is never read from the request. The field `saveNote` is added only for `'first'` or `'reminder'`, and `worker/learner-db.ts` line 331 turns any other database answer into `'none'`, so the browser can never receive an unexpected value. Nothing is logged: the `catch` is empty and `worker/save-progress.test.ts` has a test that spies on the console, with a red run for a version that logs.
- **Browser.** `src/screens/SaveNote.tsx` sends no request, and the "Not now" handler only sets a local state. There is no `localStorage`, `sessionStorage`, `document.cookie` or `console` in the files of this job. The browser test for statement 13 compares storage and cookies before and after and checks that the only requests are to the app's own address and only the ones that exist today, and a red run turns it red when "Not now" writes to storage. No call to an AI, voice or speech service, and no third party.
- **The "Add your email" address.** `ADD_EMAIL_PATH` is the fixed string `/account/email`, used in `window.location.assign`. It carries no query string, no session id, no `saveNote` value and no learner data. It is not built from the answer or from user input, so there is no open redirect. The note never reads the Worker's `saveNote` text for display (only a yes or no).
- **Rendering.** All text is fixed copy in `src/screens/save-note-copy.ts`, shown as React text. No `dangerouslySetInnerHTML`. The Worker's answer text is never put on the screen.
- **Storage, consent, location, retention, export and deletion.** Nothing new is stored, so no consent, EU location, retention, export or deletion path is affected. No recording is involved. The "Not now" choice is not remembered anywhere, as the spec says, and `evidence/13-17-no-package-route-privacy-change.txt` shows `git diff --stat` prints nothing for `src/privacy`, `worker/personal-data`, `worker/providers`, the package files and `wrangler.jsonc`.
- **Dependencies.** No change to `package.json`, `package-lock.json` or the workflows (checked with `git diff --stat main...HEAD`). No new package.
- **Secrets.** `git grep` over `factory/jobs/18-save-progress/` (the evidence and the notes) finds no token, key, password or email address. The only hit for a secret word is the line "Secret scan (gitleaks): success". The test uses fixed fake learner ids only.
- **Earlier tests.** `worker/test-fakes.ts` gains a default `'none'` fake and no earlier assertion was changed or removed, so no protection was weakened. `SaveNoteDb` as a separate interface is a sound choice: in production `databaseFor` returns the real Supabase client for every route, so the method is always present, and the fallback in `noteDatabaseFor` only ever applies to older test fakes. It cannot reach another client than the learner's own.
- **`pageshow` guard.** It only hides the note when the browser restores the page from its back forward cache. It cannot show anything, so it cannot show the note to a wrong person.
- **Same first session completed twice.** The note appears both times. This is the owner's intended behaviour, it is pinned in `[save-progress 7]`, and it reveals nothing the caller does not already have.

## For the owner to look at closely

- The wording for "Your account": the "Not now" line tells the learner they can add an email "later from Your account", which relies on job 11's page still being linked from the front door. If job 15 or job 17 changes where the account page is linked, this sentence needs a check.
- Because the note only appears for a guest after a saved session, a guest who clears their browser before adding an email loses the account in 90 days (job 8 and 11 behaviour). The note does not change that and does not claim more.
- The function reads the token claim `is_anonymous`. If Supabase ever renames or drops that claim, the function returns `'none'` for everyone (the safe direction) and the note would silently disappear. pgTAP test 21 pins the missing claim case, but nothing would alert you.

Result: pass
