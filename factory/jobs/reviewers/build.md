# reviewers (fast route)

The owner's calls of 24 November 2026: a public page at `meetaleksi.com/reviewers` where native Finnish speakers sign up to check the Finnish in Aleksi, guarded by the same Turnstile check as Start, kept until the owner deletes a sign up, with the same short email alert as feedback. Spec: `factory/jobs/reviewers/spec.md`. Flag: look closely (personal data of people with no account, a new table, a public form).

## Round 1

### What was built

- **The page.** `/reviewers` is drawn by the app shell (`index.html`), like the pages under `/learn`, so it uses the locked design system as it is: the page frame with the landscape band, the app's text fields, the status line and the primary button. It is the one app page outside `/learn`. `forwardFor` in `src/lib/app-paths.ts` now keeps `/reviewers` instead of sending it to the landing page. The page needs no account, sets no cookie and calls no `/api` route until Sign up. The words are the spec's, word for word. The three field labels are shown above the fields (the third label is too long to fit inside an empty field at 375 px), through a new `showLabel` option on `TextField`. The privacy link sits on its own line under the small print, so its 44 px tap area does not stretch a line of text.
  - Why the app shell and not a separate entry like the landing page: the landing page is prerendered with a strict CSP that allows no outside script and no request, so it would need a second CSP and a second entry just to allow Turnstile. The app shell already loads Turnstile on the road, sends no CSP header of its own (the same as the road today), and the Worker serves it unchanged for any listed page route. Adding `/reviewers` to `PAGE_ROUTES` and `run_worker_first` is all the Worker needs. A visit to `/reviewers` is counted like any other page (country and day only, no cookie). On the owner host `/reviewers` goes to the owner page, like every other page route.
- **The form flow.** Sign up checks the fields in the browser with the same rules as the Worker (`src/lib/reviewer-signup.ts`), then posts them to `POST /api/reviewers`. The Worker answers `check_needed` with the public site key, the Turnstile check runs in a `CheckSlot` above the button (with its own quiet line), and the form is sent again with the token. A second tap, a forced click or Enter while sending is ignored (a ref guard plus the busy button).
- **The route** (`worker/reviewers.ts`). Same origin JSON only, body capped at 4 KB. Fields checked: name 1 to 100 characters, a valid email of at most 254, thank-you name at most 100, no control characters; anything else is 400 with the field's name, before any check or save. Then the Turnstile token is checked with the guest route's own check (`worker/providers/human-check.ts`), which now takes an `action`, so a real token must name the `reviewers` action and this address. No token, a refused token or a check that cannot run saves nothing. Then one row is saved. Answers set no cookie. Nothing is logged.
- **Limits.** The database allows at most 3 sign ups from one email address and 200 in all on one Helsinki day. The Worker also refuses a sixth sign up from one internet address on one Helsinki day, counted in memory only per running copy of the Worker; the address is never stored or logged. 429 `limit` for any of them.
- **The database** (`supabase/migrations/20261124104750_reviewer_signups.sql`). `private.reviewer_signups` (id, name, email, thanks_name, created_at) with checks on every column, two indexes, everything revoked from public, anon, authenticated and service_role, row level security on and no rule. `public.sign_up_reviewer(text, text, text)` (security definer, anon only) checks every field again and the daily limits. `public.owner_reviewer_signups()` and `public.owner_delete_reviewer_signup(uuid)` (authenticated only) answer only an account on `private.owners` with a live sign in, as `owner_dashboard()` does, and null to anyone else. No row links to an account, so nothing goes into `export_my_data()`.
- **The owner page.** A "Reviewer sign-ups" section (`src/screens/OwnerReviewers.tsx`) under Feedback: newest first, name, email, thank-you name and date, plain text only. Each sign up has a Delete, which asks "Delete the sign-up from (name)? This cannot be undone." with "Delete for good" and "Keep it". The owner host gained `GET /api/owner/reviewers` and `POST /api/owner/reviewers/delete` (`worker/owner.ts`), behind the same three locks as the dashboard: Cloudflare Access, the Worker's Access token check, and the owner's own sign in checked by the database. The dashboard's sign in checks moved into one shared helper; its answers are unchanged (its tests pass unchanged).
- **The alert.** `worker/providers/feedback-alert.ts` now has one private sender used by both alerts. `sendFeedbackAlert` behaves exactly as before (its tests are unchanged and pass). `sendReviewerAlert` sends "New reviewer sign-up on Aleksi" with only the Helsinki time and the owner page link, never a name or email (the function is not given them), with its own 30 minute gap in memory, and nothing without `BREVO_API_KEY` and `FEEDBACK_ALERT_TO`. It runs after the answer through `waitUntil`, and a failure never changes the answer.
- **Privacy.** `src/privacy/data-inventory.ts` has `NO_ACCOUNT_ITEMS` with "Reviewer sign-ups" (what, why, legal reason, "Until the owner deletes it", and asking for deletion at hello@meetaleksi.com), shown in the notice under "From people with no account:". `HOW_LONG` gained one sentence, "Your rights" gained `REVIEWER_RIGHTS`, and Cloudflare's entry says the sign up form runs the same Turnstile check. The Brevo comment notes the second alert (no personal data goes to Brevo, so its public text is unchanged).
- **Records.** `docs/conventions.md` has the `[reviewers N]` label row, and `docs/data-model.md` a "Reviewer sign ups" section.

### For the owner to decide or check

- **"The Worker's server role".** This Worker holds only the publishable key (`worker/owner.ts`: "No stronger key exists here", and `tests/personal-data.test.ts` forbids a service key in `worker/`). So the Worker writes as anon through `sign_up_reviewer`, the same pattern as the visit count and crash reports. Anyone who had the publishable key could call that function without Turnstile; the key lives only in Worker settings. The table itself gives anon nothing.
- **"From one address".** Read both ways: the database limits one email address (3 a day) and all sign ups (200 a day), and the Worker limits one internet address (5 a day, in memory per running copy, never stored). The in memory count is best effort: Cloudflare may run several copies.
