# Security review: 14-analytics, round 1

Reviewed 30 October 2026 against `git diff main...factory/14-analytics` (head `5715f92`), the spec's 33 "Done when" statements and threat model, and `build.md` with its seven deviations. Read only; no code changed.

## Findings

No must fix findings. No should fix findings. Four notes.

1. **Note.** `src/lib/crash-reporter.ts` line 49 (`credentials: 'omit'`). On the live owner host, Cloudflare Access lets a request through only when the browser sends its `CF_Authorization` cookie, and `credentials: 'omit'` leaves that cookie out. So crash reports from the owner page, including "Send a test error", will probably be stopped by Access at go live, and README "Owner page setup" step 5 would fail. The local tests pass because they add the Access token header to every request. This is a working problem, not a data leak. A fix that keeps the privacy rule: send `credentials: 'same-origin'` only when the page is on the owner host, or accept it and remove step 5's claim. The Worker still never reads sign in cookies on `/api/crash`. The go live job should check this.
2. **Note.** `supabase/migrations/20261030101645_analytics.sql` lines 42 to 62 (`count_visit`). Anyone who has the Supabase address and the publishable key can call `count_visit` directly, with any country and no limit. The key stays in the Worker today, so this is hard to reach. The spec accepts that visits can be pushed up. The damage is bounded: at most 677 rows a day (every two letter code plus `T1`), and no personal data.
3. **Note.** `worker/crash.ts` line 112 (`reportWorkerCrash`). A Worker exception's message is cleaned of emails, ids, tokens and long digit runs, but the Worker has no list of typed values to remove, as the browser does. I found no Worker code today that puts a learner's answer, transcript or feedback text into an error message (every `JSON.parse` of a request body is inside a `try`). The privacy notice line "nothing you typed or said is included" depends on that staying true. A later job that throws an error carrying learner text would break it without a test going red.
4. **Note.** `supabase/migrations/20261030101645_analytics.sql` lines 371 to 377 (`owner_dashboard`). The database lock (owner list plus live sign in) is the only lock on a direct call to Supabase. If the owner uses the same PuhuScribe account to learn on the app host, that account's token also sits in the app host's cookie. The cookie is HttpOnly and no app host route calls `owner_dashboard`, so I found no path to misuse it. The owner could still choose to use a separate account for the owner page.

## Looked at closely, and passed

- **Who can read what.** `private.visit_tallies`, `private.crash_reports` and `private.owners` have every privilege revoked from `anon`, `authenticated`, `service_role` and `public`, with row level security on. `public.feedback` gives learners select and column limited insert (`user_id`, `screen`, `message`), with policies tied to `auth.uid()`. Nobody can update or delete through the API. pgTAP checks each of these from the catalogue and by trying as each role.
- **Multi condition rules (AGENTS.md lessons).** `owner_dashboard` has one failing case per condition (not on the list, sign in ended, `anon`). Each has a red scratch run where only its own test failed. Checked each test can fail only for its own reason. Inserting feedback for another learner is refused only by the WITH CHECK policy, because the daily limit trigger counts the other learner's rows as 0 under row level security. Setting `created_at` is refused only by the column grant. The crash group cap test stays under 300, and the total cap test uses a new group. Statement 14's six token refusals each change one thing in an otherwise valid token, and the "always allow" break turned them red.
- **Deviation 2, `public.my_owner_rows()`.** Security definer, empty `search_path`, execute for `authenticated` only, filtered by `auth.uid()`. A learner gets `[]`, and the test fails if the filter is removed because the owner's row is seeded. It tells a caller only whether they themselves are an owner. This is safer than opening the private schema.
- **Deviation 6, local test key.** `ownerKeySource` uses `OWNER_ACCESS_LOCAL_JWKS` only when `OWNER_HOSTNAME` is `localhost`, `127.0.0.1` or `[::1]`, and the owner branch runs only when the request's own hostname equals `OWNER_HOSTNAME`. A live request can never carry a loopback hostname, so production would need two wrong settings and an impossible request. The CI step writes these values only in the browser job, not in the preview deploy job. The private key lives in `.wrangler/` (git ignored, mode 600) and is not in the uploaded test artifacts. README tells the owner never to set the variable live. `worker/owner.test.ts` covers both sides.
- **Deviation 4, CI password.** `PGOPTIONS` passes the throwaway local database's fixed password (`postgres`, already in `LOCAL_DB_URL` in the same workflow) to one psql session. No hosted secret is involved. Elsewhere the file skips, and the whole file rolls back.
- **`vite preview` with `cors: false`.** Only the local preview server changes, and it now matches production. The Worker never sends `Access-Control-Allow-Origin`, and `privately()` removes it on every owner host answer.
- **Deviation 5, `MF-CF-Blob`.** Used only by a browser test. No Worker code reads it; the live Worker reads only `request.cf.country`.
- **Owner host locks.** Access token check (job 13's `hasValidAccessToken`: RS256, issuer, audience, `exp`, team domain and AUD shape) runs before any routing. Only the listed `/api` routes are answered. `/api/guest` is not among them, and email sign in uses `shouldCreateUser: false`, so no account is made there. The dashboard is GET only and refuses another `Origin`, `same-site` or `cross-site`. Private headers are on every owner host answer, including the 500 path. The redirect target is the fixed `/owner`, so it is not an open redirect. Files and the single page fallback on the owner host are served without the Worker, as the spec accepts, so only Access guards them, and they hold no data.
- **Flooding and poisoning.** Feedback is limited to 5 a Helsinki day under an advisory lock per learner. The trigger is a volatile row trigger, so a multi row insert is counted too. Crash reports are limited to 300 an hour and 30 per group under a global lock. Every field is checked again in `report_crash`, with frames limited to an exact key set. Bodies are capped at 8 KB before parsing. Country must be two capital letters or `T1` in both the Worker and the database.
- **Personal data in crash reports.** Allow list parsing refuses unknown keys. Paths become `:id`, queries are stripped, and only own bundle files are kept as frames. The browser label is coarse and the user agent is dropped. The table has no user, address or agent column. The browser sends with no cookies. The 30 day `pg_cron` deletion runs daily as the spec says, so a report can live up to about one day past 30 days.
- **Rendering.** Feedback and crash text is rendered as React text, with no `dangerouslySetInnerHTML` and no link building. The feedback page's back link comes from a fixed allow list keyed by `?from=`.
- **Export and deletion.** Feedback and the owner row are in `export_my_data()`, and both cascade with `auth.users`, so job 11's deletion and clean up cover them. Earlier tests gained seed rows and list entries only. No assertion was removed.
- **Secrets and dependencies.** No key, token or email in the diff or evidence (checked with `git grep`). No new npm package. `dblink` is used only in a test file that rolls back.

Result: pass
