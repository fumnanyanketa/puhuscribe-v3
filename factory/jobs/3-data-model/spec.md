# Job 3-data-model: Data model

Scope item 3. Needs a decision. Date: 20 October 2026. Builds on jobs 1-stack and 2-smoke as merged on main.

## What it is

This job designs the database every later feature stores its data in, and builds it in the test database. It holds two kinds of data, kept strictly apart. Learning content: the units, the dialogues line by line in spoken and written Finnish with audio for each, every word's form and its short explanation. Learner data: which forms each learner is reviewing and when each is due, every review, how far they got in each session, and their voice consent. The database itself refuses to show a learner any Finnish that the native reviewer has not approved, and refuses to show one learner another learner's data. It also loads v2's 104 starter sentences as reference material, so they can be reused when units are written.

## Done when

Each statement is checked by a command, by the GitHub checks, or by a database query on the test project. New tests are labelled `[data N]` with the statement number they protect. "Content tables" means `units`, `dialogues`, `dialogue_lines`, `tokens` and `forms`. "Learner tables" means `cards`, `review_logs`, `sessions` and `consents`. "Reference tables" means `source_sentences` and `lemma_ipa`. "A learner" means the `authenticated` role with JSON Web Token (JWT) claims for one user id, which is how a Supabase guest and a Supabase email account both reach the database.

1. **The tables exist in code, and only these.** New migrations in `supabase/migrations/` create the content, learner and reference tables, with the columns, keys and links listed under "The entities" below, plus the enum types listed there. A pgTAP test lists the tables in `public` and fails if any other table exists (so a streak or vocabulary bank table cannot appear unnoticed). `visits` and its 22 tests stay unchanged.
2. **Permissions are written out for every new table.** Each migration removes every permission from `anon`, `authenticated` and `service_role` on each new table and sequence, then grants only what the "Who can do what" table below says. Row level security (the per-row access rules) is on for every new table. A pgTAP test checks the exact permissions of each role on each table.
3. **Review is scheduled per form, matching the imported scheduler.** `cards` has one row per learner per form (primary key `user_id, form_id`). Its columns match the `Card` type in `src/lib/fsrs/types.ts` one to one (same names, `card_state` enum values `new`, `learning`, `review`, `relearning`), and its defaults match `createEmptyCard()`. `review_logs` columns match the `ReviewLog` type, plus `user_id`, `form_id` and `mode` (`typed` or `spoken`). TypeScript types generated by the Supabase CLI from the migrated schema are committed, and a Vitest test builds a card with `createEmptyCard()` and `FSRS.schedule()` and assigns every field to the generated insert types for `cards` and `review_logs` without a cast. `npm run typecheck` passes.
4. **Both registers, both with audio.** Each `dialogue_lines` row has the spoken text (`text_puhe`), the written text (`text_kirja`), an English gloss, and a storage key for the spoken audio and for the written audio. The database refuses to mark a line approved unless both texts, the gloss, both audio keys, the approval time and the approval reference are present (pgTAP: each missing field is refused).
5. **Nothing unapproved can be read.** Acting as a learner, pgTAP proves:
   - approved units, dialogues, lines, tokens and forms can be read;
   - a draft or retired unit, dialogue, line or form cannot be read;
   - an approved line inside a draft dialogue, or an approved dialogue inside a draft unit, cannot be read;
   - tokens of an unapproved line cannot be read.

   Acting as `anon` (the publishable key with no sign in), every content table refuses to be read.
6. **An approved line or form cannot change silently.** While a line, dialogue, unit or form is approved, the database refuses any change to what a learner sees (Finnish text, gloss, audio keys, form surfaces, form name, the one line "why") and any change to that line's tokens. To change it, the content must first be set back to draft, which hides it from learners until it is approved again. pgTAP covers a refused edit, a refused token change, and an edit that works after un-approving.
7. **Learners cannot write content, and reference data is closed.** Acting as `anon` or as a learner, inserting, changing or deleting rows in any content table fails, and reading, inserting, changing or deleting reference tables fails.
8. **A learner reaches only their own rows.** Using two test learners, A (a guest, `is_anonymous: true`) and B (an email account, `is_anonymous: false`), pgTAP proves for each learner table that A can read and write their own rows as the table allows, cannot read, change or delete B's rows, and cannot add a row carrying B's user id. The same holds with A and B swapped.
9. **Nothing unmet is reviewed.** A learner cannot create a card for a form unless they have a session for an approved dialogue that contains that form and whose `step_reached` is at least `understand`. pgTAP: refused before such a session exists, refused when `step_reached` is `hear`, accepted once it is `understand`.
10. **The session step is stored.** `sessions` stores the learner, the dialogue (empty for a review only session), `step_reached` (an ordered enum: `hear`, `understand`, `say`, `keep`, `use`; empty until the first step is finished), the start time and the end time. A learner can start a session and move its step forward. pgTAP covers both.
11. **Voice consent is recorded as a history.** `consents` adds one row per choice: kind (`voice_processing` or `voice_recording_retention`), given or withdrawn, the version of the consent text shown, and the time. A learner can add and read their own rows and cannot change or delete any row. The current choice is the newest row of each kind. No table in this job stores audio, a recording or a transcript of the learner.
12. **Guests can become email accounts without losing anything.** Every learner table links to `auth.users(id)`, the id Supabase keeps when a guest adds an email. No access rule mentions `is_anonymous`. pgTAP proves that the same learner id reads the same rows with `is_anonymous: true` and with `is_anonymous: false`.
13. **Export and deletion are possible, and content holds no personal data.** Every table with a `user_id` column links it to `auth.users(id)` with `on delete cascade` and has row level security on. A pgTAP test reads the database catalogue to check this for every such table, so a future table that forgets fails the check. Deleting a test user from `auth.users` removes all their rows from every learner table (pgTAP). No content or reference table has a column that identifies a learner or the reviewer.
14. **Content in use cannot be deleted.** Deleting a form, line, dialogue or unit that a card, token or session points to fails (`on delete restrict`). Content is retired instead. pgTAP covers a refused delete.
15. **v2's 104 starter sentences load, and load again without duplicates.** A script reads the 104 sentence pairs from v2 at commit `9c8d0a083d6209e0135efe20f88db99ff9c867e4` (`supabase/seeds/05_island_sentences.sql`), applies the corrections file `content/v2-starter/corrections.tsv` (subject to owner's call 1), and writes one migration that upserts them into `source_sentences`, keyed on (`source`, `source_ref`) = (`v2-starter`, `1` to `104`). A test fails if a correction's "before" text does not match v2 exactly, or if the migration's rows differ from v2 plus the corrections. In the database check, the load SQL is run a second time on the same database, and pgTAP then proves there are exactly 104 rows with the expected text. The 104 rows are not readable by any learner.
16. **v2's pronunciation data loads.** Subject to owner's call 3: the same script reads the 514 lemma to IPA pairs from v2's `supabase/migrations/20260607000003_word_ipa_from_kaikki.sql` and writes them into `lemma_ipa` with their source and licence ("English Wiktionary via kaikki.org, CC BY-SA 4.0"), as an upsert keyed on the lemma. Re-running leaves 514 rows. Not readable by any learner.
17. **The security tests can fail.** A scratch branch that adds a rule letting any learner read every card turns the database check red. The branch is deleted and its pull request closed. The red run is linked in `build.md`.
18. **The checks run as in job 2.** The database check applies every migration to a throwaway local database, runs all pgTAP tests, re-runs the load SQL and runs the import tests again. The apply job pushes the migrations to the test project and runs the same tests there; a second run applies nothing. All existing checks stay green. No test is deleted or weakened.
19. **The model is written down.** `docs/data-model.md` lists every table in one or two plain sentences, who can read and write it, which job first uses it, and how to load v2's data again. The README "Database changes" section links to it.
20. **No new running costs.** Everything stays on free plans; the README "Running costs" list stays at €0.

Product rules from `AGENTS.md` that apply: nothing unapproved is served; nothing unmet is reviewed; review is scheduled automatically with no self rating (the log stores the grader's rating, never a learner's own); both registers with audio; GDPR minimum data with export and deletion possible; audio discarded by default; agents use only the test database; never delete or weaken a test; no placeholders (no empty tables for later jobs); the "Not in v3.0" list is binding.

### The entities

Content tables use `bigint` ids generated by the database, plus a natural key that stays the same across databases, so the content pipeline (job 5) can re-publish with upserts without changing ids that learner rows point to. Learner tables use `uuid` ids. Every learner table has `user_id uuid not null default auth.uid() references auth.users(id) on delete cascade`.

| Table | Purpose | Key columns | Unique and links |
|---|---|---|---|
| `units` | A real situation tied to an A1 "can do" statement | `slug`, `position`, `title_en`, `title_fi`, `can_do_en`, approval columns | `slug` unique, `position` unique |
| `dialogues` | One short dialogue in a unit | `unit_id`, `slug`, `position`, `title_en`, approval columns | `slug` unique; (`unit_id`, `position`) unique; `unit_id` restrict |
| `dialogue_lines` | One line in both registers | `dialogue_id`, `position`, `speaker` (a role label such as "Barista"), `text_puhe`, `text_kirja`, `gloss_en`, `audio_puhe_key`, `audio_kirja_key`, approval columns | (`dialogue_id`, `position`) unique; `dialogue_id` restrict |
| `tokens` | One word of a line in one register, linked to its form | `line_id`, `register` (`puhe` or `kirja`), `position`, `surface`, `form_id` (empty for words that are never reviewed, such as names) | (`line_id`, `register`, `position`) unique; `line_id` and `form_id` restrict |
| `forms` | The thing that is reviewed: one analysed word form with its written and spoken shape | `lemma` (base form), `form_tag` (canonical key built from the Voikko analysis; job 5 sets the exact format), `analysis` (the Voikko reading as JSON, optional), `surface_kirja`, `surface_puhe`, `form_name_en`, `why_en`, approval columns | (`lemma`, `form_tag`, `surface_kirja`, `surface_puhe`) unique |
| `cards` | Review state per learner per form | `user_id`, `form_id`, `due`, `stability`, `difficulty`, `elapsed_days`, `scheduled_days`, `reps`, `lapses`, `state`, `last_review`, `created_at` | primary key (`user_id`, `form_id`); `form_id` restrict |
| `review_logs` | One row per review, append only | `user_id`, `form_id`, `rating` (1 to 4, from the grader), `mode`, `state`, `due`, `stability`, `difficulty`, `elapsed_days`, `last_elapsed_days`, `scheduled_days`, `review_time` | (`user_id`, `form_id`) links to `cards`, cascade |
| `sessions` | One sitting of the loop | `user_id`, `dialogue_id` (empty for review only), `step_reached`, `started_at`, `ended_at` | `dialogue_id` restrict |
| `consents` | Voice consent history, append only | `user_id`, `kind`, `granted`, `notice_version`, `created_at` | |
| `source_sentences` | v2's 104 starter sentences as reference for content writing | `source`, `source_ref`, `text_kirja`, `text_puhe`, `gloss_en`, `note` (v2 commit, v2 review date, corrections file) | (`source`, `source_ref`) unique |
| `lemma_ipa` | v2's pronunciation data per base form | `lemma`, `ipa`, `source`, `licence` | `lemma` primary key |

Approval columns on units, dialogues, lines and forms: `status` (enum `draft`, `approved`, `retired`), `approved_at`, `approval_ref` (a pointer to the reviewer's signed review record, for example a file and row in the repository; job 5 decides where those records live). No reviewer name or email is stored.

Enums: `content_status`, `finnish_register` (`puhe`, `kirja`), `card_state` (same strings as v2's `State`), `review_mode` (`typed`, `spoken`), `loop_step` (`hear`, `understand`, `say`, `keep`, `use`, in that order, so "at least `understand`" is a plain comparison), `consent_kind`. Postgres can add enum values later without a breaking change.

How later jobs fit without a breaking migration: job 6 adds its usage event table; job 8 adds tables for speaking attempts (transcript and feedback class) and opted in recordings; job 14 adds analytics. Each is a new table. Nothing in this job changes for them.

### Who can do what

| Role | Content tables | Learner tables | Reference tables |
|---|---|---|---|
| `anon` (publishable key, no sign in) | nothing | nothing | nothing |
| `authenticated` (a guest or email learner) | read, only rows that are approved with approved parents | `cards`: read, add, change own. `review_logs`: read, add own. `sessions`: read, add, change own. `consents`: read, add own. No deletes | nothing |
| `service_role` | nothing | nothing | nothing |

Content and reference rows are written only by migrations through the database connection, as in job 2. Job 5 decides how the content pipeline publishes, and grants itself what it needs then. Rules follow Supabase's guidance: each rule names its role with `to authenticated`, compares `user_id` with `(select auth.uid())`, and every column a rule filters on has an index. Helper functions for the triggers live in a schema the API does not expose (`private`), with `search_path` set to empty.

### Choices

| Choice | Pick | Runner up | Why the runner up lost |
|---|---|---|---|
| What a guest is | A Supabase anonymous sign in. Guests get the `authenticated` role and a real user id; their JWT carries `is_anonymous: true`. Adding an email later keeps the same user id, so every row stays attached (job 9 builds this) | A guest stored only on the device, merged into an account at sign up | Device data is lost on a device switch, cannot be protected by database rules, and needs a merge step that can lose or double progress. Scope item 6 asks for a real account |
| Where the 104 sentences go | Their own reference table, never readable by learners. A sentence reused in a unit becomes a new dialogue line and is approved in its dialogue | Load them as dialogue lines | They are 104 separate sentences, and the dialogue is the unit of content (PRD section 5). Lines need a unit, a dialogue, tokens, forms and audio that the 104 do not have |
| How "nothing unapproved" is enforced | Database rules: read rules filter on approval status and parent status; check constraints refuse an approval with missing parts; triggers freeze approved content | Filtering in app code, or database views | App filtering fails open the day one query forgets it. Row level security is Supabase's documented access mechanism and applies to every path into the database |
| Changing approved content | Refused while approved; un-approve first, then approve again | Automatic reset to draft on any edit | A silent reset hides content from learners without anyone noticing. A refusal makes the pipeline say what it is doing, and PRD section 9 asks for re-approval of changed lines only |
| Card key | Composite primary key (`user_id`, `form_id`) | A separate uuid plus a unique pair | One card per learner per form is the rule; the composite key states it directly |
| Review state columns | One column per scheduler field, same names as `types.ts` | One JSON column holding the whole state | JSON cannot be indexed on `due` for "what is due today", and type drift would go unnoticed |
| Consent storage | One row per choice, with the consent text version | One row per learner with two true or false values (PRD sketch) | GDPR Article 7(1) says the controller "shall be able to demonstrate that the data subject has consented", and 7(3) gives a right to withdraw at any time. Two booleans lose when and to what text |
| Link to the user | Each learner table links straight to `auth.users(id)` with cascade delete | A `profiles` table between them | No profile data is needed yet (minimum data). Supabase's docs recommend linking to `auth.users` primary key with `on delete cascade`. A profile table can be added later without breaking anything |
| Acting as a learner in pgTAP | Insert test users into `auth.users` inside the rolled back test, then `set_config('request.jwt.claims', ..., true)` and `set local role authenticated` | Basejump's `supabase_test_helpers` package (Supabase's extended pgTAP page) | It needs the dbdev installer plus the `http` and `pg_tle` extensions in every database, the test project included, for helpers at version 0.0.6. Setting the claims by hand is what PostgREST itself does and needs nothing installed |
| Loading the 104 and the IPA | A generated migration of upserts, built by a checked script from v2's files plus the corrections file | `supabase/seed.sql` | Supabase runs seed files on `supabase start` and `supabase db reset`, which are local. The test project gets changes through `db push` (job 2), so data that must reach it belongs in a migration |
| The `visits` table | Kept. Job 6 removes it together with the "Hei!" page | Drop it now | The front page and job 2's browser tests use it today. It holds no personal data |

## Out of scope

- Any screen, component or styling (jobs 4 and 6).
- The content pipeline, its publishing path and any role or key it needs; writing units, dialogues, tokens or forms for real (jobs 5 and 10). This job creates the tables only. Test rows exist only inside rolled back pgTAP tests.
- Sign in screens, switching on anonymous sign ins in the test project or in `supabase/config.toml`, CAPTCHA, upgrading a guest to email, export and delete buttons, guest clean up (jobs 6 and 9).
- Tables for speaking attempts, recordings, usage events, analytics, feedback or the waitlist (jobs 6, 8, 14, 15).
- Storage buckets for audio and how audio keys are formed (job 5).
- Anything on the PRD's "Not in v3.0" list: no streak, milestone, rank or celebration tables; no vocabulary bank (no learner word lists, no word counts); no practice mode, grammar lesson, island, sentence bank, mnemonic, YKI or language toggle tables. v2's `words` table is not carried over.
- Changing `/api/health` (job 2's open item about what its database check proves goes back to the manager; it is not part of the data model).
- A Supabase secret key, a personal access token, `supabase link` or Supabase Branching.

## Risks and flags

- **Look closely: database and access rules.** This job writes the rules that keep learners apart and keep unapproved Finnish away from learners. Every later feature depends on them. The tests are the main protection, and statement 17 proves they can fail.
- **Look closely: learner data and consent.** It creates the first tables that will hold learner data and the voice consent record. No learner data is stored by this job. Test users exist only inside rolled back test transactions, including when the tests run on the test project.
- **Look closely: Finnish learning content.** The 104 sentences are loaded into the test project as reference rows that no learner can read. Their wording, the corrections and their use in v3 go to the owner and the reviewer (owner's calls 1 and 2). Sentences 45 to 104 come from the owner's Finnish course notes (SKK1), written by a teacher; whether the teacher's material may be reused in a commercial app was not checked. The origin of sentences 1 to 44 is not recorded in v2 (v2's attribution file says its earlier content was generated by Claude).
- **Licence.** The IPA is CC BY-SA 4.0 (attribution and share alike). Storing it is fine; showing it to learners later needs the attribution line from v2's `docs/content-attribution.md`, and whether share alike reaches the app's data was not checked with a lawyer.
- **Changes reach the test project before approval.** As in job 2, migrations are applied to the test project when the database tests pass on the pull request. If this job is rejected, its tables stay there until a later migration removes them. Job 2 left an open item to gate this on owner approval once learner data exists; this job adds the first learner tables, so the manager should decide now.
- **Book fair rate limit (for job 6, urgent).** Supabase allows 30 anonymous sign ins per hour per IP address by default. At the Helsinki Book Fair (22 to 25 October), many visitors on the same venue wifi share one IP address, so guest starts could be refused after 30 an hour. The limit can be raised in the dashboard. Supabase also "strongly recommends" CAPTCHA or Cloudflare Turnstile for anonymous sign ins.
- **Abandoned guests pile up.** Supabase does not delete anonymous users automatically. Each guest who never returns keeps a user row and their progress. Job 9 needs a clean up rule (owner's call 4).
- **Deletion details for later jobs.** Supabase cannot delete a user who owns Storage objects, so job 8 must delete kept recordings first. A deleted user's access token stays valid until it expires, so job 9 should keep tokens short lived.
- **Un-approving hides content mid course.** When the pipeline un-approves a line to fix it, learners stop seeing that line (and its dialogue's flow) until it is approved again. Job 5 should fix content in batches.
- **Running costs.** €0. The new tables and the 618 reference rows are far below the free plan's 500 MB. Each check run takes a little longer; `build.md` reports the minutes.

## Owner's calls

None of these is decided. Each has a recommendation. No call involves money or an email address.

**1. The reviewer's corrections to the 104 sentences.** The scope says to apply them before import. They are not in v2's repository: the review sheet's "OK / fix" column is empty everywhere I looked, and v2's notes say you were to send the marked up list.
- A. You find the marked up list (paper, photo, document, email) and give it to the builder. The builder types it into `content/v2-starter/corrections.tsv`, one row per change (sentence number, spoken or written, before, after). Your reviewer checks the typed list against their markings before it is loaded, about 15 minutes of their time (my estimate). The scope's "corrected" wording is met.
- B. Load the 104 as they are in v2, marked "corrections not applied". Nothing reaches learners either way, and any sentence reused in a unit is checked again by the reviewer in its dialogue. The scope line about corrections is then changed to say so. Costs no reviewer time now.
- C. Do not import the 104 at all. Units are written fresh by the pipeline. The scope and PRD lines about migrating them are dropped.
- Recommendation: A if you can find the list this week; B if not. The job can build everything else meanwhile.

**2. What the 104 sentences are for in v3.**
- A. Reference material only. The pipeline may borrow a sentence when writing a unit's dialogue, and the borrowed line is then approved by the reviewer in its dialogue, both registers and audio, like every new line. Matches the PRD's rule that every line is approved and the dialogue is the unit.
- B. Treat the June 2026 v2 review as approval for any sentence reused word for word. Saves some reviewer time, but that review was of isolated sentences, before v3's standard (Helsinki adult speech in 2026, approved in context), and its corrections are unknown.
- Recommendation: A.

**3. v2's pronunciation data (IPA for 514 base words).**
- A. Import it now into a reference table that learners cannot read. Free. A later job decides whether learners ever see IPA, with the Wiktionary attribution.
- B. Leave it out. v3's word card (base form, form name, one line why, both registers) does not show IPA, and the data came from v2's vocabulary list, which v3 does not use. The scope line about pronunciation data is dropped.
- Recommendation: A. It follows the scope and the PRD and costs nothing; leaving it unused is harmless.

**4. How long an unused guest account is kept (needed by job 9, not this job).** A guest who never returns leaves a user id and their progress behind.
- A. Delete guest accounts with no activity for 30 days (Supabase's own example). Least data kept. A guest returning after a month starts over.
- B. 90 days. Covers someone who tried the app at the book fair and returns in the new year. More data kept.
- C. Never delete automatically. Simplest, but stores data with no end date, which GDPR's storage limitation principle argues against.
- Recommendation: B, stated in the privacy notice.
