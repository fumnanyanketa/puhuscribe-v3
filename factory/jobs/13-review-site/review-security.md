# Security and privacy review: 13-review-site

Reviewer: security review agent, 22 October 2026. Branch `factory/13-review-site`, head `6d30b7e`, compared with `git diff main...HEAD`. I read the code only. Nothing was deployed, and no `.env*` file was read or searched.

## Findings

### 1. Should fix (low). The build follows a symlinked dialogue folder

- **File.** `scripts/review-site/build.ts` lines 98 to 104, plus `readTitle` at line 84 and the `content/reviews` check at line 119.
- **Risk.** `lstatSync` only refuses a symlink at the last part of the path, so if `content/drafts/<slug>` (or `content/drafts`) were a committed symlink, the build would copy `round-<n>.html` files and read `draft.json` from wherever it points, outside the listed drafts.
- **Fix.** Run `lstatSync` on `content/drafts` and on `content/drafts/<slug>` as well, and refuse either one if it is not a plain folder. Add one Vitest case for a symlinked slug folder. No symlinks are committed under `content/drafts` today (checked with `git ls-files -s`).

### 2. Should fix. The docs do not say where the reviewer's email goes

- **File.** `docs/content-pipeline.md` line 41 ("Who gets in") and line 60.
- **Risk.** The docs say only that no email is written into the repository. They leave out that Cloudflare keeps the reviewer's email in the Access policy and its sign-in records, and sends the one-time PIN email. The spec's Risks section says the storage period and location of those records were not confirmed, and that they may be outside the EU. Removing the reviewer from the policy and the users list frees the seat but does not erase those records. So the owner has nothing to point to when telling the reviewer what happens to their email, which the spec asks the owner to do.
- **Fix.** Add two plain sentences at line 41: Cloudflare (Exentrik account) holds both emails in the Access policy and in its sign-in records, and sends the PIN email; how long it keeps them, and whether they stay in the EU, is not confirmed, so tell the reviewer before their first sign-in. At line 60, add that this removal does not delete Cloudflare's sign-in records.

### 3. Note. A pull request branch in this repository can still reach the Exentrik token

- **File.** `.github/workflows/review-site.yml` lines 87 and 106 to 113, and 147 to 155.
- **Risk.** GitHub gives repository secrets to `pull_request` runs from branches in the same repository. A branch that edits this workflow (or adds a new one) could read `CLOUDFLARE_REVIEW_API_TOKEN` and deploy, or change the Access app, in the Exentrik account. The `if:` on line 87 only guards the workflow as written on main. The same is true today for `CLOUDFLARE_API_TOKEN` in the preview job. The code cannot fix this: environment secrets with a "main only" rule need GitHub Pro for a private repository (the branch protection API also answered "Upgrade to GitHub Pro" for this repository).
- **Fix.** Nothing in code. Keep the token as narrow as possible: the Exentrik account and the exentrik.co zone only, with no DNS rights unless Cloudflare refuses the custom domain without them, and no Access rights the deploy does not need. If the owner later moves to GitHub Pro, put the four secrets in a `review-site` environment limited to `main`.

### 4. Note. In CI, wrangler takes over the name `puhuscribe.exentrik.co` without asking

- **File.** `review-site/wrangler.jsonc` line 162 together with the deploy at `.github/workflows/review-site.yml` lines 137 to 139.
- **Risk.** When there is no terminal, the installed wrangler sets `override_existing_dns_record` and `override_existing_origin` to true (`node_modules/wrangler/wrangler-dist/cli.js` around line 164461). So the first deploy silently replaces any existing DNS record or Worker domain named `puhuscribe.exentrik.co`. Only that one name is affected. MX records and Email Routing are not touched.
- **Fix.** None in code. Before the first deploy, the owner confirms that exentrik.co has no `puhuscribe` record (build.md owner step 5 already says this).

## Checked and passing

- **Access token check** (`review-site/handler.ts` lines 80 to 101). It reads the `Cf-Access-Jwt-Assertion` header (header names ignore case) and nothing else, not the `CF_Authorization` cookie. It uses jose `jwtVerify` with only `RS256` allowed, issuer equal to the team domain, audience equal to the AUD tag, and `exp` required. Clock tolerance is jose's default of 0. Any error refuses the request, including a failed key fetch, so it fails closed. The team domain must match `https://<team>.cloudflareaccess.com` and the AUD must be 64 hex characters, otherwise everything gets 403. Keys come only from `<team>/cdn-cgi/access/certs`, so a bad setting cannot make it fetch keys from another address. The key set is created once per Worker instance (line 49). jose caches the keys and fetches them again only when an unknown key id appears, at most once every 30 seconds, so Cloudflare's key rotation is handled. Claims are never decoded and the email is never read. There are tests for alg none, a missing expiry, a wrong audience, a wrong issuer and an expired token, and the "always allow" break proof is in evidence.
- **No way around the token check.** Every request goes through the Worker first (`run_worker_first: true`). The only path that answers without a valid token is a non GET or HEAD method, which gets a 405 with one plain line and no file. A missing file or a path outside the allow list gets 404 only after the token check, so a visitor without a token cannot tell which files exist.
- **Path handling.** Only `/`, `/index.html`, `/robots.txt` and `/<slug>/round-<n>(.html)` are looked up. I checked how the browser's address parser (the same standard the Workers runtime uses) handles tricky paths. `//robots.txt`, `%2F`, a trailing slash, `/.wrangler/...`, `;`, `%00`, `round-01` and `.json` are all refused. `..`, `%2e%2e` and `./` are cleaned up before the check and can only reach the allowed files. The file lookup is sent as a plain GET of the cleaned address, with no cookies or conditional headers. Only listed slugs are served, because `dist-review/` holds nothing else.
- **Response headers.** Every response carries `X-Robots-Tag`, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`, `nosniff` and a Content-Security-Policy that forbids framing. That includes 403, 404, 405 and redirects. The index gets the strict policy. Review pages get only `frame-ancestors 'none'` and keep the policy built into the page by job 7.
- **Build script.** Each listed slug must match `^[a-z0-9]+(-[a-z0-9]+)*$` and appear only once. The list file must hold only `dialogues`. Each page must be named `round-<n>.html`, be a plain file and not a symlink, and be at most 25 MiB. The `review` folder must not be a symlink. All checks run before anything is written. `dist-review/` is deleted and rebuilt each time, and the pages are copied byte for byte with `copyFileSync`. Titles are escaped in the index. Slugs go into the HTML without escaping, which is safe because the slug pattern allows only lower case letters, digits and hyphens. Draft files, audio, round JSON, briefs and returned reviews are never copied.
- **Wrangler config.** `workers_dev: false` and `preview_urls: false`. The only route is the custom domain `puhuscribe.exentrik.co`. There are no secrets, no binding besides ASSETS, and observability is off. The handler has no `console` call.
- **Workflow.** `permissions: contents: read`, and `persist-credentials: false` on both checkouts. Only GitHub's own actions are used. The pull request job has no secrets and no variables. Deploy runs only when the event is not a pull request, the ref is main and the actor is not Dependabot. The deploy job has its own concurrency group that never cancels a running deploy. The two deploy secrets are only in the deploy step and the two service token secrets are only in the live test step, with no job or workflow level `env` holding secrets. When nothing is set up yet the deploy is skipped, a partial setup fails, and badly shaped settings are refused. The secret scan runs in the same step as the tests. Only `.png` and `.webm` files are uploaded, and only when the scan comes back clean. They are kept 14 days in a private repository.
- **Live tests and the service token.** With the token set, `playwright.config.ts` turns trace off and drops the HTML report. HAR recording is never on. The anonymous contexts set `extraHTTPHeaders: {}` and check that no token header was sent. The downloaded review file is deleted, and the upload guard scans `test-results` and `playwright-report`, including inside zip files.
- **Dependency.** `jose` 6.2.12 is pinned exactly and is MIT licensed, published 5 September 2026 by an actively maintained project. It has no dependencies of its own. It was already in the lockfile as a dev dependency, so this job adds no new package. `npm audit` finds 0 vulnerabilities.
- **No secrets or emails.** The diff and the three commit messages hold no email address, token, JWT or long hex string. The only `@` text is the existing git author line, which this job did not add. The repository test checks `review-site/`, `scripts/review-site/`, the workflow and both e2e files for email-shaped strings.
- **Nothing touches the PuhuScribe account.** `checks.yml`, the app's `wrangler.jsonc` and `worker/` are unchanged. The review workflow never names `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` or `CF_ACCESS_CLIENT_*`, and a test checks this. The only DNS effect on exentrik.co is the one custom domain record (see note 4).

## Threat model answers, checked against the code

- **Worst case: someone holding the Exentrik token redeploys, or changes the Access policy, and phishes under exentrik.co.** The deploy runs only from main, but see note 3: a branch in this repository could reach the token. Nothing in the code can stop a token holder. If the Access app is deleted or a policy is opened by mistake, the Worker's own check (audience and issuer) still refuses every request.
- **Worst case: script hidden in draft text.** Titles in the index are escaped, the index has no script, and its policy is `default-src 'none'`. Review pages keep job 7's escaping and hashed script. No page can be framed.
- **Data to protect.** The reviewer's and owner's emails stay out of the repository, the code, the logs and the tests. Cloudflare holds them, and the docs should say so (finding 2). The tokens are only in GitHub secrets, used only in their own steps.
- **What it refuses.** Files that are not listed, requests without a valid token for this application, any method other than GET and HEAD, deploys from a pull request or another branch (in the workflow as written), and being indexed or framed. Bypass and "Everyone" rules live only in the dashboard, so the live tests are the check on them (spec statements 13 and 14).

## For the owner to look at closely, even though it passes

- **Access app setup (statement 13).** The Worker trusts any valid token for this AUD tag. Whoever the Access policy allows gets in. Check the policy has exactly two emails plus the Service Auth rule, with no Bypass and no "Everyone" rule.
- **API token scope.** The docs say the token is limited to Workers and the custom domain. Cloudflare's Workers edit right also covers Access apps (lesson from 1-stack), so the token could read or change the Access policy and the emails in it. Grant the least that lets the deploy attach the domain.
- **Service token JWT.** Not verified: whether Access adds `Cf-Access-Jwt-Assertion` to requests that use a service token. If it does not, the first main run's live tests get 403. That would show up as a red run, not as an open site.
- **Wrangler's deploy log prints the two plain variables.** These are the team domain and the AUD tag. They are identifiers, not secrets, and the repository is private.
