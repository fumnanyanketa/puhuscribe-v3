Building PuhuScribe with Claude Code, start to finish

PuhuScribe Roadmap

Here is the whole journey in six stages. Every stage is recorded as it happens: the screen, the chat with the AI, your voice over it, then the result. Before any of it, a short glossary, because the kit uses a few words that sound more technical than they are.

★

The goal we are aiming at. 50 learners finish onboarding and have their first AI conversation in Finnish without asking you for help. At least 40 percent of them come back within two weeks for another session on a different day. When that is true, it worked.

Eight terms used on this page

Skill
A saved set of instructions you run in Claude Code by typing a slash command, like /architect. Each one does one job. We installed nine from the kit and kept four of our own.
Scope
The plan. One file that lists every feature, in build order, with a checkbox for each step. The thing you look at to know what is next.
Spec
One written decision. Which database, how sign in works, what the AI tutor may and may not do. The AI builds from the spec and is not allowed to invent what the spec does not say.
AGENTS.md
The rulebook. A file at the top of the project that every AI session reads first. The stack, the commands, the house rules, the things it must never do.
Tracer Bullet
Our build style. Instead of finishing one screen at a time, you first build one very thin path that goes all the way through, from the screen to the AI to the database, and really works. Then you make it thicker, feature by feature.
Beta
The standard checking level, and our default. After a feature is built, the AI runs the real app to prove it works, then writes tests so it stays working.
GA
Short for General Availability, the industry term for "ready for the public". Here it means the full checking level. Everything Beta does, plus a second AI model reviews the code, a security sweep, a written change log, and you personally write "approved" before it counts as done. We use it for the three features that touch logins, personal data, or the AI itself.
AI
A feature that calls an AI model while the app runs. Normal tests cannot grade a conversation, so these also get an eval: a fixed set of example inputs with known good answers, scored for a pass rate.

Stage 1 · six steps, fixed order

Tech stack, rules, data model, design system

Now the first code appears, but still no features. You pick the tools, create the empty app, write the rulebook from what is really there, set up the automatic checks, decide the shape of the data, and settle the look. The kit insists on this order, and for good reason: the rulebook has to describe a real project, not an empty folder.

1.1 Choose the tools
You run /architect and have a conversation. It recommends a boring, well documented set of tools, explains the runner up and why it lost, and writes the choice to a spec. Rule of thumb it follows: one app, not many services. A normal relational database. Nothing clever.
1.2 Create the empty app
You run /develop once to make the skeleton with the chosen tools' own setup command. Nothing extra installed yet.
1.3 Write the rulebook
You run /audit. It reads the real skeleton and writes AGENTS.md: the stack, the commands to run and test things, the conventions it can see, plus our house rules from Stage 0.
1.4 Set up the safety rails
A code style checker, a type checker, a test runner, and a secret scanner. Then small hooks so Claude Code runs them automatically. These cost no tokens and never get tired.
1.5 Decide the shape of the data
Back to /architect. What is a learner, a level, a session, a mistake, a review item? This is written down once so every later feature uses the same shapes. The kit never lets you skip this one.
1.6 Settle the look
You run /canvas, our own skill. You gather references, pick one direction in a sentence, and it generates the mascot first, then every illustration in that same style, then the empty, success and error pictures. Then /develop turns the direction into real colours, fonts and spacing, and checks that text is readable in light and dark before writing a line of CSS.
End of Stage 1: an empty app that boots, with its rulebook, its data shape, and its look settled. Nothing a learner can use yet. That arrives in the very first slice of Stage 2.

Repeated for each of the ten features in stages 2 to 4

The feature routine: decide, build, prove, protect, record

From here on, every feature goes through the same routine, and the four foundation items in Stage 1 use a shorter version of it. Decide it, build it, prove it, protect it, then update the paperwork and clear the chat. Beta features stop after "protect it". GA features run the longer tail. You type each command yourself, and you are allowed to skip any step after the build. The only thing the kit really insists on is that decisions get written down.

/architect
Decide it
A conversation that ends in a spec: what done looks like as numbered statements, and where every value on screen comes from.
/develop
Build it
Checks the spec covers everything first (see the gate below). Then builds, step by step, and checks its own work.
/check verify
Prove it
Runs the real app like a user would and ticks off each "done looks like" statement. GA: saves screenshots and waits for your "approved".
/test
Protect it
Writes tests so that if a later change breaks this feature, you hear about it immediately.
/check eval
Grade the AI
Only for AI features. Runs the example set and reports a pass rate.
/check review
Second opinion
GA only. A different AI model reads the code and lists problems by severity.
/warden
Security sweep
GA only. Leaked keys, weak dependencies, risky code paths.
/document
Write it up
GA only. A plain description of what changed, written from the real changes.
/sync
Update the paperwork
Ticks the plan, marks the spec accepted, adds any new rule to AGENTS.md. Then you clear the chat and start fresh.
The gate: how the AI is stopped from guessing

Before building, /develop lists every value the feature will show or calculate, and checks whether the spec says where each one comes from. If one has no source, it stops and gives you three choices.

Decide it firstRecommended. Go run /architect, then come back.
Nothing to decideYou judge it really is a detail. Build.
Build now, write it downIt writes your assumption to a small spec marked "Assumed" and keeps reminding you until a real decision is made. The shortcut is allowed. Forgetting it is not.
When something breaks: /debug
Sort it firstIs this a real bug, a confused chat session that needs clearing, or a bad earlier decision? Each has a different fix.
Make it happen on demandA bug you cannot reproduce is a bug you cannot prove you fixed.
One theory at a timeTest it. Wrong? Throw it away, try the next. Never five random edits at once.
Fix the cause, not the symptomSmallest possible fix, look for the same mistake elsewhere, then a test so it can never sneak back.

Stage 2 · slices 1 to 3

First conversation loop, tutor quality, onboarding

The first slice is the Tracer Bullet itself: one thin path through every layer that really works. A learner signs in for real, answers three placement questions, has one short text exchange with the AI tutor, and it is all saved in the real database. Nothing is faked, it is just narrow. The next two slices thicken it: the tutor learns to hold the learner's level and correct warmly, and the front door becomes a proper onboarding. By the end of this stage a person who is not you can have their first conversation unaided. That is the first half of the goal.

2.1 First conversation loop GA AI
Real sign in through the service chosen in the stack spec, three placement questions that set a level, at least three turns with the tutor in Finnish, and the session plus one usage event saved. The spec settles voice or text first and how the level is passed to the model. This is the first time the full feature routine runs.
2.2 Tutor quality GA AI
The tutor holds the learner's level across a whole conversation, pitches its Finnish just above it, corrects warmly without breaking the flow, and refuses what the threat model says it must refuse. You build the example set, 10 to 25 sample exchanges with good answers, and the tutor has to hit the pass rate written in its spec.
2.3 Onboarding and placement Beta
A welcome flow, a short intake about goals and situation, a more careful level estimate than the three questions in slice 1, and a landing on home with a suggested first session. The spec decides how the level is estimated and what gets saved.
The payoff clip: the first time someone else sits down, finishes onboarding, and talks to the tutor in Finnish without asking you anything. Every stage before this is recorded too. This is just the one the series has been building toward.
3

Stage 3 · slices 4, 5 and 8

Accounts, spaced repetition, analytics

A great first conversation is not enough. The goal says 40 percent come back within two weeks. So this stage is about memory, in both senses. The app remembers the learner across sign ins, it brings yesterday's mistakes back today, and it counts every return so you can actually measure the goal instead of hoping. All three touch logins or personal data, so all three get the full GA treatment.

3.1 Accounts and sign in GA
Sign in already works from slice 1. This slice turns it into full account care: sign out and back in with progress intact, consent text that explains what is stored and why, and account deletion that really removes the data. The three security questions get asked and answered in the spec.
3.2 Review and memory Beta
Spaced repetition: showing a word again just before you would forget it. Due words and past mistakes come back on a schedule. This is the main reason a learner opens the app tomorrow.
3.3 Counting what matters GA
Three numbers: finished onboarding, finished a first conversation, came back within 14 days on a different day. Once this ships, the goal at the top of this page is a query you can run.
Heads up: three GA features in a row means three rounds of the long tail. Second model review, security sweep, write up, and your signature each time. It is slower. It is also where most apps leak data, so it is worth it.

Stage 4 · slices 6, 7, 9 and 10

Lessons, drills, home screen, profile

So far the learner can talk and come back. Now you add the staircase underneath the talking: words first, then the rules behind them, then repetition drills, all feeding into conversation. Plus a proper home screen that says "here is your session for today" and a profile page. This stage also has a parallel job that no skill does for you: writing the actual Finnish lessons.

4.1 Lesson player Beta
Two kinds of lesson. Chunk lessons for useful phrases, and grammar lessons taught our way: where the rule came from, the logic behind it, the rule itself, the exceptions, then examples. The spec decides where the lesson content lives and how it is loaded.
4.2 Practice drills Beta
Short drill sets. Every mistake is saved and fed into the review schedule from Stage 3.
4.3 Home screen Beta
Your progress and today's suggested session. Small enough that it may not need its own spec.
4.4 Profile and settings Beta
See and change your level, your goals, your account, your interface language.
About the content: the AI can scaffold lesson templates, but the Finnish itself, the examples, the drills and the tutor's personality are yours to write and check. Plan time for it alongside this stage, and consider filming it as its own kind of episode.
5

Stage 5 · release

Security check, pilot with ten learners, public launch

Everything is built and checked. Now you prove it with strangers. First a security sweep and a readiness checklist that blocks the release if anything fails. Then about ten real newcomers for two weeks while you watch the numbers from Stage 3. Fix what breaks, re plan what you learned, and only then open it up to the fifty.

5.1 Security sweep
/warden, our own skill. Scans the code and the entire history for leaked keys, checks every library for known holes, reads the code around logins and personal data. Anything critical blocks the release.
5.2 Readiness checklist
/liftoff, our own skill. Does the whole journey work on a real phone, not just your laptop? What happens with no internet, slow internet, empty inputs? Is the privacy text there? Can you roll back? It blocks until every line passes.
5.3 Pilot with about ten people
Two weeks. Watch the three numbers. Bugs go to /debug. Surprises go to a bare /scope, which reads the plan back and helps you reorder.
5.4 Open it up
Release to fifty, measure the goal, and start on the deferred list: language islands, and whatever the pilot taught you.
Done means proven. Fifty learners through a first conversation unaided, forty percent back within two weeks. Not "it runs on my machine".
